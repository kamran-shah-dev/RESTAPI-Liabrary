# Contributing

Thank you for your interest in contributing to the Library Management API. Contributions such as bug reports, documentation improvements, tests, and code changes are welcome.

Please follow this guide to keep contributions consistent and easy to review.

## Code of Conduct

By participating in this project, you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report unacceptable behavior through the project's issue tracker or the contact method specified in that document.

## Ways to contribute

You can contribute by:

- Reporting and reproducing bugs
- Requesting or implementing features
- Improving the REST API
- Adding or correcting tests
- Improving setup and API documentation
- Fixing typos and formatting issues

Before starting significant work, open an issue to describe the proposed change and discuss the approach with maintainers.

## Development requirements

- Java 21
- Maven, or the included Maven Wrapper
- Git

No external database is required. The application stores books, members, and borrowing records in memory, so data is cleared whenever the application restarts.

## Set up the project

Clone the repository and enter the project directory:

```bash
git clone https://github.com/kamran-shah-dev/RESTAPI-Liabrary.git
cd RESTAPI-Liabrary
```

Run the application:

```bash
# macOS or Linux
./mvnw spring-boot:run

# Windows
.\mvnw.cmd spring-boot:run
```

The API will be available at `http://localhost:8080/api`.

Build the project without starting it:

```bash
./mvnw clean package
```

On Windows, replace `./mvnw` with `.\mvnw.cmd`.

## Create a change

1. Fork the repository.
2. Create a descriptive branch from the default branch:

   ```bash
   git checkout -b fix/book-update-response
   ```

3. Make the smallest cohesive change that addresses the issue.
4. Add or update tests for behavior you change or add.
5. Run the test and build commands before submitting.
6. Commit the change with a clear message.
7. Push the branch and open a pull request.

Keep pull requests focused on one concern. Avoid unrelated refactoring or formatting changes.

## Coding guidelines

- Follow the existing Java package and naming conventions.
- Keep controller HTTP concerns in `controller`, business logic in `services`, and domain types in `model`.
- Use Spring and Java types consistently with the surrounding code.
- Validate user-facing API behavior through Spring tests where practical.
- Keep JSON field names and API paths backward-compatible unless the change is intentional and documented.
- Preserve HTTP status behavior, including `404` for missing records and `204` for successful deletes.
- Do not introduce a database or persistent storage as an incidental part of an unrelated change.

IDs are currently assigned by clients rather than generated by the API. Member dates use ISO-8601 format, such as `2026-01-15`. Borrowing creates a due date 14 days after the borrow date.

## Testing

Run the complete test suite:

```bash
./mvnw test
```

Run a focused test class:

```bash
./mvnw -Dtest=LiabraryApplicationTests test
```

Tests should cover observable behavior and edge cases. For API changes, include request and response assertions where possible. Every pull request should pass `./mvnw test` and `./mvnw clean package`.

## Reporting bugs

Create an issue and include:

- A clear description of the problem
- Steps to reproduce it
- The expected and actual behavior
- API request and response examples, if relevant
- Java and operating-system versions
- Any relevant application logs

Do not include passwords, tokens, personal data, or other secrets.

## Requesting features

Describe the feature's purpose and expected API behavior. Include example JSON requests or responses when helpful. For breaking changes, explain migration and backward-compatibility concerns.

## Pull request checklist

Before requesting a review, confirm that:

- The change has a clear scope and a linked issue, when applicable
- Tests cover the new or corrected behavior
- Documentation and API examples are updated
- The project builds and tests pass
- The code follows the existing project structure and style
- The PR summary explains the reason for the change and how to verify it
